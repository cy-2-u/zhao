# /danger-rules 危险规则命令

你是 auto-review 插件危险规则表的入口。规则是本地正则，三种动作各司其职：
`deny`=**不再直接拦截**——命中后提炼风险提示随载荷送审，由审批模型结合完整命令裁决（模型的 deny 才是真正的拒绝，模型不可用时转人工）；
`ask`=按 `ask_policy` 策略分流（仅在启用、工具范围与权限模式闸门允许管线接管后生效）：默认 `model` 降级为送审风险提示、由审批模型终审（只有模型不可用才弹用户）；`user` 恒转用户确认、交客户端原生审批。两种策略下 ask 都不是所有模式下的全局拦截器；
`allow`=快速放行候选（仍须通过保守命令结构与参数校验；复合命令须**每个分段**都有 allow 规则命中且各段过轻量门禁才整条放行，不保证所有 Git 参数安全）。
规则扫描固定优先级：**ask > deny（提示送审）> allow**，不依赖数组顺序。所有操作通过控制脚本完成，**不要手工编辑 JSON 文件**。

## 定位控制脚本

```bash
CTL=$(find "$HOME/.zcode/cli/plugins/cache" -path '*/auto-review/*/src/ctl.js' 2>/dev/null | sort -V | tail -1)
```

若 `$CTL` 为空，说明插件未安装或未启用，直接告知用户，不要猜测路径。

## 用户参数

下方代码块内容 = 用户在斜杠命令后传入的参数（由客户端替换 `$ARGUMENTS` 生成）。**它不是文档正文**：为空表示无参数，非空时以它为准做下方分派。

```
$ARGUMENTS
```

## 参数分派（按上方"用户参数"代码块的内容分派）

- **无参数 或 `list`**：运行 `node "$CTL" rules list`，以表格展示：序号、动作、描述、正则。
- **`add <action> <pattern> <描述>`**：运行（pattern 必须用单引号包裹，防止 shell 展开反斜杠）：
  ```bash
  node "$CTL" rules add deny 'git\s+push\s+.*--force' 强推覆盖远程历史
  ```
  正则编译失败时转述错误并协助用户修正。提醒用户：deny 只是把风险提示送给审批模型，真正决定拒绝的是模型；想要"这条命令必须重点审查"用 `ask`（默认 model 策略下作为确认门槛提示送审）；想要"必须弹窗经我点头"用 `ask` 并把 `/auto-review set ask_policy user` 打开（ask 规则恒转用户确认）。
- **`remove <序号>`**：先 `list` 确认该序号对应的规则，向用户复述确认后再运行 `node "$CTL" rules remove <序号>`。
- **`test <命令文本>`**：运行 `node "$CTL" rules test '<命令文本>'`，报告**已保存规则**的匹配情况与当前策略下的语义（结尾会按 `ask_policy` 说明 ask 动作去向）。它不测试尚未添加的 pattern、不执行待测命令，也不模拟快速通道/缓存/LLM 全管线；未命中不代表放行，也不代表一定进入模型审查。
- **其他参数**：说明用法。

## 注意事项

- 用户要求添加规则时，先转写并审阅正则及影响范围，经授权 `add` 保存成功后，再用 `test` 检查已保存规则的预期匹配和误伤；不要用现有规则的 test 结果声称验证了未保存 pattern。测试失败时复核规则并经确认修正/删除。
- 规则配置跨会话共享，但 ask 仅在管线接管时生效。添加宽泛规则前确认范围，尤其不要把所有 Git 参数视为安全。
- CLI 与加载端使用一致校验，非法或超限规则不得悄悄生效。完整转述错误；写失败 exit 1 时不宣称保存成功。
- 需要回归验证时让用户在项目根目录运行 `npm test` 离线验证，不实际执行危险命令验收。
