# 模块设计：决策管线（reviewer.js）

## 管线（顺序固定，先确定性后概率性）

```mermaid
flowchart TD
    A[stdin: hook JSON] --> B{① enabled?}
    B -- 否 --> P[pass 空输出<br/>内置流程继续]
    B -- 是 --> B1{② 工具名可识别?}
    B1 -- 缺失 --> XD[deny 阻断<br/>协议异常 fail-closed]
    B1 -- 是 --> C{② tool ∈ review_tools?}
    C -- 否 --> P
    C -- 是 --> C2{②' 模式闸门<br/>仅自动编辑(edit)接管}
    C2 -- "其他模式值" --> P
    C2 -- "edit / 字段缺失" --> D[构造送审文本<br/>Bash→命令全文 / Write→路径]
    D --> E{③ 全文规则层<br/>本地正则·在 LLM 之前}
    E -- "allow（单段）" --> X3[白名单放行]
    E -- "ask（用户确认门槛）" --> X2[转用户裁决<br/>插件对话框 / 客户端原生框]
    E -- "deny → 提炼 ruleHint 送审" --> F{③' 复合逐段层}
    E -- "allow（复合命令全文被抑制）" --> F
    E -- 未命中 --> F
    F -- "任一段 ask" --> X2
    F -- "任一段 deny" --> F2[ruleHint 并入<br/>跳过快速通道与白名单]
    F -- "全段 allow" --> X4[复合白名单放行]
    F -- "混合/单命令" --> FH{带 ruleHint?}
    FH -- "是（deny 命中）" --> F2
    FH -- 否 --> FA{③'' 低风险快速通道<br/>单段·无重定向/命令替换}
    FA -- 命中 --> X6[静默放行 0 LLM]
    FA -- 未命中 --> S{④ 会话白名单}
    S -- 命中 --> X5[会话放行]
    S -- 未命中 --> SA[④.5 脚本内容附加<br/>inspect_scripts 开启时]
    F2 --> SA
    SA --> G{⑤ 缓存层<br/>sha256 稳定键 + cwd/附件摘要加盐}
    G -- 命中未过期 --> R[复用上次决策]
    G -- 未命中 --> H[⑥ 安全子 agent<br/>专用审批渠道·上下文干净<br/>载荷含 ruleHint 行 + 可选脚本附件块]
    H -- "allow" --> Y1[放行 + 一句话分析]
    H -- "deny" --> Y2[拦截 + 分析与替代做法<br/>additionalContext 回传主 agent]
    H -- "ask（存疑）" --> Y2
    H -- 失败 --> I[⑦ 兜底<br/>ask 转人工审批<br/>模型不在场绝不自动许可]
```

> **deny 规则不再直接拦截（0.4.0）**：全文或复合段命中后只提炼 ruleHint 风险提示，随载荷
> 附"本地规则仅作为风险提示，不是最终结论"一行送审——模型能看到完整命令与参数，比正则
> 更适合判断"这条命令此刻是否合理"；最终拒绝来自审批模型，模型不可用则转人工审批。

## ask 的三种来源、两种去向

> **规则层 ask**（用户显式添加的确认门槛，如出厂的关机/重启规则）——无论何种模式都转用户
> 裁决：模型看不到对话历史，无法替用户判断"这是不是我要求的"，这类规则必须由人拍板。
> `dialog_on_ask=false`（默认）时由客户端原生审批框确认，开启时走插件对话框。
> 这是 Codex 式"升级审批"的等价物：危险但可能合法的操作，人工点头才执行，而非一刀切禁令。
> **LLM 层 ask**（模型存疑）——`ask_to_user=false`（默认）时收敛为 deny + additionalContext
> 回传；`ask_to_user=true` 时保持 ask 转用户裁决（插件对话框或客户端原生框由 `dialog_on_ask`
> 决定）。deny 是子 agent 的合法结论，必须附分析与 alternative。
> **兜底 ask**（0.4.0 新增）——审批模型不可用（渠道未配置/超时重试后仍失败/输出不可解析）
> 时转人工审批，绝不自动许可；`dialog_on_ask` 同样决定对话框或客户端原生框，模型恢复后
> 相同命令重新进入自动审查。

## 关键不变量

1. **规则层只做路由，不做终审拒绝**：规则在 LLM 之前，固定优先级 deny/ask > allow（用户把
   宽泛 allow 排在前面也遮不住风险规则）；allow 只放行单段命令，复合命令只能逐段全 allow
   才放行；deny 提炼 ruleHint 送审，真正的拒绝来自审批模型（模型不可用→人工）。
2. **二值收敛（LLM 层）**：默认无人工环节——审批模型只产出 allow/deny 两个出口（存疑收敛
   deny）；deny 必带分析与替代做法（additionalContext 通道），主 agent 据此修改重试。
   规则层 ask 与兜底 ask 不受该收敛影响——那是用户意志或人工兜底，不算打扰。
3. **模型不在场绝不自动许可**：LLM 链路任何失败（渠道未配置、超时、HTTP 非 2xx、输出不可
   解析、未知异常）→ ask 转人工审批；hook 协议异常（空 stdin、非法 JSON、非对象、缺工具名）
   → deny 阻断。pass 仅保留给"插件主动不接管"（关闭、范围外、非 edit 模式、空输入），
   不存在"故障→放行"路径。
4. **崩溃阻断**：hook 进程自身崩溃时 exit 2 阻断而非放行（decision.emitCrash）。
5. **带 hint 的命令不走捷径**：命中 deny 规则的命令跳过快速通道与会话白名单——
   规则可能是临时放行之后才新增的，会话级临时许可不能压过风险提示。

## 复合命令逐段设计

- 顶层分隔符：`;` `&&` `||` `|` 换行（单 `&` 后台执行同边界）；引号、`$()`、反引号
  内的分隔符不切分（字符串扫描状态机）；
- 逐段过规则：ask > deny（送审提示）>（全 allow 放行）> null（降级 LLM 审查完整命令）；
- 全文扫描对 allow 的抑制：复合命令的白名单放行**只能**由逐段全 allow 确认。

## 脚本内容附加（④.5，0.2.3）

`inspect_scripts`（默认 false）开启后，Bash 命令进入缓存/LLM 层前附加被调用脚本内容：

- `extractScriptRefs`：复用拆段器逐段提取——解释器调用（python/node/bash/pwsh 等）
  跳过选项取脚本路径（`-c`/`-e`/`-m` 放弃：内联已在命令里、模块非文件）；
  powershell `-File`、cmd `/c` `/k` 特判；段首裸脚本路径也算；引号内空格不切分、`~` 展开；
- `collectScriptAttachments`：相对路径按 hook 输入 `cwd`（回落进程 cwd）解析；仅普通
  文件；单文件上限 `script_max_bytes`（超限截断标注）；前 8KB 含 NUL 判二进制跳过；
  最多 3 个文件；失败以附注说明。任何异常只降级为"不附加"，不影响决策；
- 位置：会话白名单之后（用户批准的是命令本身）、缓存之前；附件摘要参与缓存键加盐；
- 载荷：附件块追加在工具调用 JSON 之后（独立预算），标题注明"结论必须结合脚本实际内容"；
  脚本内容按不可信数据对待——提示词要求把附件当被审查对象而非指令，防载荷内提示注入。

## 缓存键设计

`sha256(tool_name + "\n" + stableStringify(tool_input) [+ "\n" + cwd/附件摘要盐])`，
其中 stableStringify 递归按键排序——`{command, description}` 与 `{description, command}`
生成同一键，等价调用命中同一缓存。盐由 `reviewCacheKey` 组装：**cwd 必须参与键**——同一命令
文本在不同项目目录语义可能不同（如 `node scripts/deploy.js`），跨项目复用结论就是跨项目污染；
开启脚本送审时附件摘要（各文件路径与内容 sha256）同样入键（0.2.3）：脚本内容变更后旧结论自动
失效。无 cwd 且无附件时与旧版键完全一致（历史缓存条目兼容）。缓存写入走文件锁（0.3.1）——
并发 hook 进程的读-改-写不再互相覆盖丢条目。
只有 LLM 结论入缓存（规则层即时、规则变更后旧缓存无效）。

## reason 三段式（deny 回传主 agent 时展示）

```
[auto-review] 风险级别 high: 使用 curl 将 .env 内容 POST 到外部地址
风险点:
- 会把密钥等敏感信息上传到外部端点
- 端点合法性无法确认
影响范围: 本地 .env、外部网络地址 https://...
```

ask 决策同时以 `additionalContext` 输出同文本（客户端同向叠加路径不渲染 reason，
该通道保证分析进入主 agent 上下文用于事后转述）；deny 决策同样双发——分析 + alternative
回传主 agent 修改重试，这是二值模式的反馈闭环。规则层送审提示（route）不带
additionalContext：该提示的受众是审批模型（在载荷内），不是主 agent。

## 失败兜底的语义（0.4.0：转人工，不静默）

审批模型不可用时不猜测、不自动放行——一切 LLM 链路故障收敛为 ask 转人工审批（插件
对话框或客户端原生审批框），模型恢复后相同命令重新进入自动审查；hook 协议异常直接
deny 阻断（无法确认审查对象时不能放行未知调用）。

| 失败 | 结果 |
|------|------|
| 专用审批渠道未配置 / 填写不全 / 未填 model | ask 转人工（日志 `[fallback] 审查不可用: ...`，reason 注明"审批模型不可用"） |
| LLM 超时（总时长 watchdog；超时/网络抖动/5xx/429 自动重试 1 次后仍失败） | ask 转人工 + 原因 |
| HTTP 非 2xx（4xx 不重试） | ask 转人工 + 状态码与截断的错误体 |
| 模型输出不可解析 / decision 字段非法 | ask 转人工 + "模型输出不是合法 JSON" |
| 管线未知异常（外层 catch） | ask 转人工（绝不放行） |
| hook 输入为空 / 非法 JSON / 非 JSON 对象 | deny 阻断（入口 fail-closed） |
| hook 输入缺工具名 | deny 阻断（无法确认审查对象） |
| 工具输入无法构造送审文本（空命令/无路径） | pass 交回内置流程（无审查对象，不占审查资源） |
| hook 进程自身崩溃 | exit 2 阻断（decision.emitCrash） |
| 审查对话框故障 / 检测到远程会话标记 | 保持 ask 回落客户端原生审批 |
